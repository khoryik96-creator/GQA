# GQA dependency and container supply-chain controls

## Reproducible dependency inputs
- `apps/web/package-lock.json` and `apps/runner/package-lock.json` were generated by npm 10 (Node 22) directly from the repository's real package manifests in a temporary GitHub Actions job.
- The build and CI paths use `npm ci`, which rejects a stale or incompatible package-lock rather than silently updating resolution. Dependabot updates require review and CI.
- `apps/api/go.sum` records Go module hashes generated with Go 1.27.4. API Docker builds run `go mod download`, `go mod verify`, and `go build -mod=readonly`; Go CI uses the checksum data instead of `go mod tidy`.
- Go's `go.mod` may be normalized during `go mod tidy`; changes to it and `go.sum` are committed together. CI must never regenerate the dependency graph silently.

## Scheduled and PR security verification
- `.github/workflows/security-checks.yml` checks reachable Go vulnerabilities, high/critical production npm advisories, Go vet, and the locked dependency graph.
- `.github/workflows/container-supply-chain.yml` builds the local API, web and Playwright runner images from the current branch. Each image is scanned with Trivy. The scan fails on *fixable critical* OS or library advisories and generates an SPDX JSON SBOM artifact using Syft.
- These scans run on pull requests, pushes to `main`, and periodically. A green scan does not imply there are no other vulnerabilities, no malicious dependencies, and no vulnerabilities announced after the scan.
- The SBOM artifacts are CI evidence. They are not a signature or attestation of a deployed artifact.

## Updating dependencies safely
1. Open a Dependabot PR or update a manifest, regenerate the relevant lockfile with the supported toolchain, and commit both.
2. Review package version changes, license terms, lockfile churn and security advisories.
3. Require foundation tests, Docker integration, migration recovery, and supply-chain workflows on the final commit before merge.
4. Verify the running image and target revision in any real deployment; local development images are not currently signed or provenance-attested.

## Important remaining gaps
- Docker image bases currently reference version tags, not content-addressed digests. Base-image drift remains possible until digests are pinned, audited and refreshed automatically.
- Third-party GitHub actions are version-tag pinned rather than commit-SHA pinned.
- No image signing, verified deployment provenance, policy-backed exception register, or production-grade container release promotion exists.
- Host Docker broker privilege and Chromium sandbox boundaries remain unchanged; this project remains restricted to controlled fixture testing and local-only operation.
- High-severity but not critical container vulnerabilities are reported by Trivy only when configured to include them; the current critical gate intentionally prioritizes fixable critical findings. Revisit the threshold before production release.
